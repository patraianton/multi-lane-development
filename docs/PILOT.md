# Пилот «без доски»: как ведём спринт с 15.09.2026

Простой документ для сессии CTO, которая запускает спринт по новому процессу. Он заменяет на время
пилота цепочку доски (проверка по спеке → ревью → починки → QA-раунды). Доска на паузе. Решение Антона
15.09.2026: «мы не NASA, у нас простой агрегатор».

## 1. Зачем

Старая цепочка чинила следствие: полоса писала «сделано», а требования были пропущены. В ответ появлялись
новые проверяльщики, круги и потолки. Итог по замерам 10–15.09: на один PR до 13 прогонов Codex на `ultra`
с пятью помощниками, 26 кругов и 18 часов на большом PR, а CI на критическом пути — 5 % времени. Каждый
проверяльщик — новый агент без памяти, и каждый круг приносит новые замечания на старый код.

Новый принцип: **доказывает тот, кто делал; проверяет один и с памятью; человек смотрит картинки.**

## 2. Что убираем, что оставляем

Убираем на время пилота: агентов по спеке (S-круги), агентов-ревьюеров (R-круги), круги починок больше
одного, потолки, ожидание квитанций стейджинга, QA-раунды с нарезкой тикетов и сворачиванием, `ultra` и
помощников на полосах, полную локальную проверку перед каждым пушем.

Оставляем без изменений: один тикет на спеку; короткий `pr-ci` на каждый пуш; независимая приёмка для защищённых
областей (миграции и схема, вход, выкат и кэш, сборщик); автовыкат .lv с main; Amp QA-орб после выката;
режим бэкапов базы; никаких сборок на Windows Антона.

Правило вливания (решение владельца 17.09.2026, заменяет прежнее «только на зелёный `pr-ci-full`»): вливаем на
зелёный короткий `pr-ci` точной головы. Полная проверка идёт на `main` после вливания и каждую ночь. Метка
`full-ci`, полный прогон и независимая приёмка до вливания нужны только PR, который трогает защищённую область.
Защищённая область — это миграции и схема, вход (`lib/auth/`, `auth/`, `middleware.ts`, `app/api/auth/`), сборщик,
`ops/`, выкат (`deploy-prod.yml`), `Dockerfile` и `docker-compose`; точный список путей — `PROTECTED_PATHS` в
`.github/workflows/pr-ci.yml`. Строка `pr-ci-full` на PR без метки — не полный прогон, а сторож: зелёная, если правка
вне защищённых областей; красная при зелёном коротком `pr-ci` — правка задела защищённую область и ждёт метку.

## 3. Роли

| Кто | Что делает |
|---|---|
| Антон | Даёт спеку. Смотрит скриншоты и бой две минуты. Слово нужно только для денег, исходящего, стратегии. |
| Окно CTO (Claude, Fable) | Режет спеку в один тикет, запускает полосу, читает вердикт, разруливает споры, вливает на зелёный короткий `pr-ci` (метку `full-ci` ставит только для защищённой области). После каждого запуска полосы или CI сразу ставит фоновое ожидание; пока идёт спринт — держит себя в цикле, не заканчивает. |
| Полоса (Codex на Mac или на сервере полос) | Пишет код, сама доказывает каждое требование; вёрстку — глазами: снимает свою страницу и сверяет с макетом до пуша. Открывает PR, пишет DONE с таблицей. |
| Проверяющий (Amp-орб, стоячий тред) | Просыпается по DONE, один проход, один вердикт комментарием. Не больше 30 минут. |
| CI | Короткий `pr-ci` на каждый пуш — по нему и вливаем. Полная проверка — на `main` после вливания, каждую ночь и по метке `full-ci` для защищённых областей. Сетка от регрессий. |
| Amp QA-орб | После выката ходит по бою, заводит тикеты `[prod-qa]`. Уже работает (`prod-qa-amp.yml`). |
| Женя | Приёмка по тем же скриншотам и таблице. Вернул — один тикет-починка, без нового раунда. |

## 4. Процесс по шагам

**Шаг 0. Подготовка (один раз, ~2 часа, до первого тикета).**
- Навык проверяющего `.agents/skills/pr-review/SKILL.md` в репозитории продукта: что читать, как выглядит
  вердикт, запрет второго NO-GO.
- Воркфлоу `pr-review-amp.yml`: на комментарий `DONE` (или метку `review`) будит стоячий тред Amp
  (`amp threads continue $AMP_REVIEW_THREAD_ID -ox "Review PR #N"`), таймаут 30 минут. Секрет `AMP_API_KEY`
  и переменная треда уже есть по образцу `prod-qa-amp.yml`.
- Скрипт-сторож таблицы: пустая колонка «чем доказано» → орб не просыпается, полосе пишется одна строка.
- Проверяющему нужны два доступа, иначе он пишет «не ходится»: логин/пароль стейджинга в сообщении пробуждения
  (секрет репо) и доступ приложения Amp к `autopase-evidence` (клик владельца организации в настройках GitHub).
  Пока доступа к evidence нет — окно CTO зеркалит спек и скриншоты в ветку `artifacts/<тикет>` (папка
  `artifacts/task-<тикет>/`), и полоса обновляет зеркало перед каждым DONE.
- Доска на паузу: задача `mld-board` на Windows Антона выключена на время пилота.
- В `maclane`/запуске полосы по умолчанию `-m gpt-5.6-sol -c model_reasoning_effort=xhigh`, помощников 1
  (`agents.max_concurrent_threads_per_session=1`; 0 Codex не принимает). Никакого `ultra`. `gpt-6-astra` — не по
  умолчанию и не по старой памяти, а отдельное решение окна CTO на конкретный большой тикет при проверенной квоте
  (Astra сжигает недельную квоту в разы быстрее: 07.09 и 15.09 подписки вылетали). В тикете записать модель прогона —
  на пилоте меряем круги и часы по моделям: возможно, дороже на участке, но дешевле на дистанции (Антон, 15.09).
- Глаза полосы (с 20.09.2026). Они есть на сервере полос codex-dev (полосы lane-1..3, `docs/FLEET.md`); на Mac и
  Hostinger их нет. Команда «снять страницу» и правило для исполнителя лежат в репозитории продукта:
  `tools/look/look.mjs` (адрес, ширина, файл; ~7 секунд; нажатия — `--click`, своё для тикета — `--setup`; печатает
  ошибки страницы и элементы, у которых текст не помещается в рамку) и `docs/VISUAL-LOOP.md`. Браузер для неё на
  сервере полос стоит в `~/kitchens/autopase.lv/garage-v1/look-tool`, команда находит его сама. Перед тикетом с вёрсткой окно CTO: поднимает из папки
  полосы сайт с живой перезагрузкой на `http://127.0.0.1:3210` с данными, нужными тикету (копия базы стенда или боя);
  проверяет, что он отвечает; пишет в задание адрес сайта, команду его перезапуска и путь к макетам.
  Такой сайт на сервере один: памяти 7 ГБ, второй сайт и сборку рядом не запускать.

**Шаг 1. Тикет.** Окно CTO делает из спеки ОДИН тикет в GitHub (правило от 04.09 остаётся). В тикете —
таблица требований из спеки с пустой колонкой «чем доказано». 15 минут.

**Шаг 2. Запуск полосы.** Окно CTO пишет `~/kitchens/autopase.lv/TASK-<тикет>.md` по шаблону из раздела 5
и запускает одной командой (`mac autopase.lv "Прочитай ~/kitchens/autopase.lv/TASK-<тикет>.md и выполни
целиком"`). Это запуск на Mac. Тикет с вёрсткой идёт только на полосу сервера полос, где есть глаза (шаг 0): задание
кладётся в `~/kitchens/autopase.lv/` на том сервере, запуск — `hz <номер полосы> "Прочитай … и выполни целиком"`.
Полоса не ждёт ревью и полную проверку; короткий `pr-ci` своей головы она дожидается, но смотрит на него раз в
4–5 минут, а не каждые 30 секунд.
Вёрстка по макетам в тикете есть — окно CTO заполняет в задании блок «Вёрстка по макетам» целиком: числа с макета
(размеры, отступы, цвета), а не «сделай как нарисовано»; всё, что открывается по нажатию (карта, окна, панели,
выбранные состояния) — это снимается с первого круга; адрес сайта, команда перезапуска, путь к макетам.
Вёрстки нет — блок из задания удалить. Пустых `<…>` в задании не оставлять.
Сразу после запуска окно CTO ставит фоновое ожидание конца прогона и держит себя циклом. Прежде чем оставить сторожа
в фоне, один раз выполнить его команду проверки руками и убедиться, что она находит нужный прогон и печатает его
состояние: сторож с неверным шаблоном молчал 45 минут при зелёном прогоне.

**Шаг 3. PR.** Полоса открывает PR, дожидается зелёного короткого `pr-ci` (~12 мин; смотрит раз в 4–5 минут) и только
потом пишет комментарий `DONE` с заполненной таблицей и ссылками на скриншоты в `Baltic-OrangesLV/autopase-evidence`.

**Шаг 4. Проверка.** Воркфлоу будит Amp-проверяющего. Один проход: таблица против спеки, скриншоты
рядом с макетами, дифф, стейджинг головы (если собран). Один комментарий: `GO` или `NO-GO` со списком
не длиннее десяти строк. Что не ломает поведение и не пропускает требование — в список «доводка», не блокер.

**Шаг 5. Починка (максимум одна).** `NO-GO` → окно CTO читает. Согласно — одна команда полосе «почини
список из вердикта», шаги 3–4 повторяются один раз. Второй `NO-GO` — решает окно CTO (чинит само,
вливает с оговоркой или несёт Антону). Третьего круга нет.

**Шаг 6. Вливание.** `GO` → окно CTO вливает на зелёный короткий `pr-ci` точной головы. Выкат .lv идёт сам.
Полная проверка проходит на `main` после вливания и ночью; покраснела — чинить первой очередью. Только для
защищённых областей: поставить `full-ci`, дождаться зелёного `pr-ci-full` на точной голове и независимой приёмки
комментарием в PR — и только тогда вливать.

**Шаг 7. Взгляд человека.** Антон или Женя смотрят скриншоты из PR и бой. Находки → один тикет-починка,
он идёт по шагам 2–6. Amp QA-орб после выката заводит свои тикеты, они идут так же.

## 5. Шаблон задания для полосы (TASK-<тикет>.md)

```
# Тикет #<номер> — <название>

Спека: <путь или ссылка>. Ветка: feat/<номер>. Репозиторий: Baltic-OrangesLV/vincheck-latvia.

Сделать всё, что в спеке. Три рынка — одна правка (CLAUDE.md).
Каждая команда gh — с `--repo Baltic-OrangesLV/vincheck-latvia`: у копии на полосе нет репозитория по умолчанию,
первая же команда без него падает.

Перед КАЖДЫМ пушем — только это, не больше:
  npx eslint <изменённые файлы>
  npx tsc --noEmit
  npx vitest run --changed origin/main
ОДИН раз перед DONE — полный `npx vitest run` (без сборки и без Playwright): в репозитории ~150 тестов-сторожей
читают исходники через readFileSync, и `--changed` их не выбирает (пилот №1: 12 таких падений всплыли только
на полном CI и стоили третьего прогона). Сборку и Playwright гоняет CI.
Тесты, которым нужна база, по голому vitest не суди: он идёт по общей базе 127.0.0.1/postgres и даёт ложные падения
(20.09 — 29 штук). Упал в полном прогоне тест с базой — запусти `node scripts/ci-local.mjs --scoped`: это тот же набор,
по которому короткий pr-ci судит твою голову, на одноразовой базе и без сборки. Зелёный — падение было шумом
окружения, одной строкой в отчёт; красный — чинить. Без ключа `--scoped` не запускать: пойдёт сборка.

Вёрстка по макетам:
  Сайт с живой перезагрузкой: <адрес>. Не отвечает — один раз подними: <команда перезапуска>.
  Снять страницу: `node tools/look/look.mjs <адрес> <ширина> <файл.png>`. Макеты: <путь>. Правило целиком —
  `docs/VISUAL-LOOP.md` в репозитории, прочитай до первой правки.
  Числа с макета: <размеры, отступы, цвета>.
  Снять: <каждая поверхность и всё, что открывается по нажатию> — на ширинах из «Сделано», п. 2.
  До пуша сними СВОЮ страницу, открой снимок и макет как картинки, сверь. Пушить только сошедшееся.
  «Сверено с макетом» без снимка своей версии = не сделано.
  Сайт не поднялся с одного раза или снимок не получается — окружение не чини: напиши в отчёте
  «снять страницу не могу: <что именно>» и остановись.

Увидел в задании незаполненное <…> — не угадывай: напиши об этом в отчёте и остановись.

Запрещено: трогать защищённую область (миграции/схему, вход, выкат, сборщик, ops/, Dockerfile и docker-compose) без
пометки «защищённая область» в PR; удалять или пропускать тесты; ждать ревью; ставить метку full-ci; клонировать
макеты и evidence в /tmp или рядом с полосой — копия одна, в ~/kitchens/autopase.lv/evidence/ (нет её — склонируй
один раз ровно туда, дальше только `git pull`); работать дольше 6 часов подряд — остановись и напиши, где ты.

Ожидание pr-ci после пуша: `gh pr checks <номер PR> --repo Baltic-OrangesLV/vincheck-latvia` не чаще раза в
4–5 минут (между проверками `sleep 240`), без `gh run watch`: 20.09 одиннадцать прогонов потратили по 15–25 минут
и большую часть памяти на «still running». Ждать не дольше 40 минут. Прогон не начался или не закончился — проверь,
что у PR нет конфликта с main (при конфликте CI не запускается: подтяни main), и напиши в отчёте
«pr-ci не дождался: <что показывает gh pr checks>». Дальше не жди.
Красный короткий pr-ci — твоя поломка, чинить. Красный `pr-ci-full` при зелёном коротком pr-ci значит одно: правка
задела защищённую область. Метку не ставь, коммитов ради него не делай: поставь в описании PR пометку «защищённая
область», перечисли задевшие её файлы и напиши это первой строкой в DONE — метку ставит окно CTO.

«Сделано» = ВСЁ ТРИ вместе:
  1. PR открыт, pr-ci короткий зелёный.
  2. В evidence-репо (~/kitchens/autopase.lv/evidence/<спринт>/<тикет>/) лежит скриншот КАЖДОЙ поверхности
     из спеки рядом с её макетом — на 1440×900, 390×844 и 360×800 и на каждой ширине, которую называет спека
     (обычно 430 и 1280), запушено.
  3. Комментарий DONE в PR с таблицей ниже, без пустых строк.

| № | Требование из спеки (дословно, коротко) | Чем доказано (тест / скриншот / адрес) | Файл |
|---|---|---|---|
| 1 | ... | ... | ... |

Строка без доказательства = задача не сделана. Не пиши «сделано» словами — только таблица.
Последняя строка отчёта: DONE #<номер> <sha головы>.
```

Требования: <n> из <m> доказаны.

 1. §<раздел> — спека говорит … — код/скриншот показывает … — путь:строка
Доводка (не блокирует, в отдельный тикет после выката):
 - ...
Стейджинг: обошёл <адрес> | не собран | не ходится (ACCOUNT_AUTH=0 — кабинет)

## 7. Что меряем на пилоте

Сравниваем с 10–15.09 (данные в `_conveyor/autopase.lv/reports/ci-time-2026-09-15/`):

| Показатель | Было | Цель |
|---|---|---|
| Прогонов Codex на PR | до 13, с помощниками до 65 | 2 (полоса + одна починка) |
| Кругов на большом PR | 12–26 | ≤ 3 |
| Часов от тикета до вливания | 18–24 | ≤ 8 |
| Полных прогонов pr-ci на PR | ≈ 2 | 0; для защищённой области — 1 |
| Возвраты Жени | «в большинстве случаев» | считаем штуки |

**Пилот №1 — тикет #2334 (карточка v12, 36 требований), 15.09.2026:** прогонов Codex на PR — 3 (работа, починка по
вердикту, починка тестов-сторожей после полного CI) плюс один прерванный старт; проверок — 2 (оба NO-GO: первый —

сторожам). Возвраты Жени — считать после его взгляда.

**Пилот №2 — тикет #2344 (+#2345), доводка карточки v12 после взгляда Жени, 16.09.2026:** шаг 7 сделан страницей
«макет против реализации» (Lavish, 36 снимков круга 2 рядом с эталонами + форма решений); Женя отметил все 8 пунктов
«сейчас». Прогонов Codex на PR — 2 (работа + одна починка по вердикту); проверок — 2 (NO-GO 6/8: ряд миниатюр на 1440

(две попытки: браузерный тест автосалона G-08 мигнул на первой, зелёный на перезапуске). Короткий pr-ci первой головы был

Найдено при подготовке задания: v12 убрал старый блок расчёта, который писал черновик заявки Nord; новый блок его не
писал — регрессия, а не недостающая функция. Урок: при редизайне сверять с тем, что делал старый модуль.
Оснастка: секрет `STAGING_BASIC_AUTH` заведён, wake-сообщение проверяющего с этого PR его передаёт (сработает со следующего

## 8. Чего не делать

- Не запускать панели агентов для проверки. Проверяющий один.
- Не заводить тикет на каждую находку. Одна починка — один тикет.
- Не ставить `full-ci` на PR вне защищённых областей; на защищённой — не раньше `GO`: метка на открытом PR делает
  каждый следующий пуш полным прогоном.
- Не отдавать вёрстку по макетам исполнителю, который не может открыть свою страницу. Расхождения не пересказывать
  словами — числа с макета и снимки.
- Не караулить CI чаще раза в 4–5 минут — ни полосе, ни окну.
- Не закрывать окно, пока полоса или CI в работе, без фонового ожидания: так потеряны 17,5 и 10,5 часа на
  пилотах №5–6.
- Не переписывать RULES.md под пилот. Этот документ — единственное описание пилота; итог пилота решает,
  что попадёт в RULES.md.
